# Moomoo Bot 全自動運用化改修ロードマップ

## 現状の診断サマリー

バックテスト上では高いリターン（CAGR 38%、総リターン 597%）を示すが、**フルアクティブ運用時の最大ドローダウン-41%、回復に1年8ヶ月**という現実があり、現状のままでは精神的・運用的にハンズオフ運用は不可能。

---

## Phase 1: 基盤整備（最重要：1〜2週間）

### 1.1 状態永続化層の構築
**問題**: `RiskState`（ピーク資産値、停止フラグ）がメモリ上のみ。再起動でリセットされる。
**改修**:
- SQLiteファイル（`~/.moomoo_bot/state.db`）で以下を永続化：
  - `risk_state`: peak_account_value, halted, halted_reason, updated_at
  - `position_log`: 日次のポジションsnapshot（リカバリ用）
  - `order_history`: 注文ID、銘柄、数量、価格、ステータス、約定情報
  - `equity_curve`: 日次の資産推移（ドローダウン分析用）
- `orchestrator.py` の `run_auto_monitor` で、サイクル開始時にDBから状態を復元

### 1.2 約定確認・ポジション追跡
**問題**: 注文を出した後、約定したかどうかの確認がない。ポジションが意図した通りになっているか不明。
**改修**:
- `MoomooPaperTradeClient` に `wait_for_fill(order_id, timeout_sec)` メソッド追加
- 注文後、次のサイクルで `get_order_frame` を使ってステータス確認（FILLED_ALL / PARTIAL / CANCELLED）
- 約定数量と注文数量の差分を検知し、未約分があれば次回サイクルで再注文
- `orchestrator.py` に `reconcile_positions` 関数追加：目標ポジション vs 実ポジションの差分を監視

### 1.3 設定の動的反映
**問題**: `get_settings()` が `@lru_cache` でキャッシュされており、`.env` 変更後も再起動が必要。
**改修**:
- `Settings` クラスに `reload()` メソッド追加
- `run_auto_monitor` の各サイクル冒頭で `.env` のmtimeを確認し、更新があればreload
- 特に `max_drawdown_pct`, `stop_loss_pct`, `market_shock_drop_pct` は動的変更可能に

## Phase 2: リスク管理強化（最重要：2〜3週間）

### 2.1 動的ポジションサイジング（ボラティリティターゲティング）
**問題**: 常にフルインベストメント。ボラティリティが高い時も同じリスクを取っている。
**改修**:
- `config.py` の未使用項目 `volatility_lookback_days`（デフォルト21日）を有効化
- 各銘柄の過去N日ボラティリティを計算し、`target_exposure = base_weight * (target_vol / current_vol)` で調整
- 例: 目標ボラティリティ15%で、個別銘柄の実現ボラが30%なら、ポジションサイズを50%に縮小
- 全体のポートフォリオボラティリティも監視し、 `max_volatility_percentile` を超えたらキャッシュ比率を上げる

### 2.2 未使用設定の有効化：フォールバック資産
**問題**: `fallback_asset_symbol` と `fallback_allocation` が設定にあるが未使用。
**改修**:
- モメンタム銘柄がトレンドフィルターをすべて落ちた場合（`no_symbols_above_trend`）、自動的に `fallback_asset_symbol`（例: US.BND）に `fallback_allocation` %を配分
- これにより「キャッシュ or フルインベスト」の二択を避け、債券等への逃避経路を確保

### 2.3 ドローダウン制御の強化
**問題**: 最大ドローダウン15%で停止するが、停止後の自動復帰ロジックが不完全。
**改修**:
- **段階的縮小（Gradual De-risking）**: ドローダウン10%でポジションを50%縮小、15%で全売却（段階的）
- **自動復帰条件の明確化**: 回復率5%（`max_drawdown_reset_pct`）を超えたら、段階的にポジションを復元（一括復帰ではなく、3回に分けて25%ずつ）
- `drawdown_state` DBテーブルで、段階的縮小の履歴を追跡

### 2.4 相関リスク・セクター集中リスクの監視
**問題**: 同じセクター（テック）に複数銘柄が選ばれる可能性。
**改修**:
- 銘柄のセクター情報を設定または外部APIで取得
- 同セクター銘柄は最大1銘柄まで（またはセクターウェイト上限20%）
- ポートフォリオ全体の平均相関が0.8を超えたら、キャッシュ比率を自動で20%上昇

## Phase 3: 戦略多角化（重要：3〜4週間）

### 3.1 コア・サテライト構成の自動運用対応
**問題**: `satellite` コマンドで分析できるが、`auto-run` に組み込まれていない。
**改修**:
- `config.py` に `satellite_weight`（デフォルト0.23）を追加
- `orchestrator.py` で、毎月リバランス時に以下を実行：
  1. アクティブ戦略で目標銘柄を決定
  2. `satellite_weight` %をアクティブ銘柄に配分
  3. 残り `(1 - satellite_weight)` %をベンチマーク（VT）に配分
  4. VTポジションも同時にリバランス（現在はアクティブ銘柄のみ）
- これにより、ドローダウンをVTの水準に近づけつつ、アクティブ部分でアップサイドを狙う

### 3.2 週次リバランスオプション
**問題**: 月次（21日）のみ。トレード回数が少なく、統計的信頼性が低い。
**改修**:
- `rebalance_days` に 5（週次）を選択可能に
- 週次の場合、lookback期間を短縮（例: 63日、126日）した戦略パラメータセットも検索対象に
- バックテストで週次 vs 月次の比較レポートを自動生成

### 3.3 マルチタイムフレーム確認
**問題**: 単一のトレンドフィルターのみ。
**改修**:
- 日次・週次・月次のトレンドがすべて同方向の時のみエントリー（複合フィルター）
- 例: 日次価格 > 日次200MA かつ 週次価格 > 週次40MA かつ 月次価格 > 月次10MA

### 3.4 逆ボラティリティウェイト
**問題**: 等分ウェイト（イコールウェイト）のみ。
**改修**:
- 選択銘柄の逆ボラティリティ（1 / σ）に比例して配分
- ボラティリティが高い銘柄のウェイトを自動的に抑制

## Phase 4: 監視・通知・異常対応（重要：2〜3週間）

### 4.1 Webhook/通知システム
**問題**: 異常時に気づく手段がない。
**改修**:
- `config.py` に `webhook_url`（Discord/Slack/Line等）を追加
- 以下のイベントを通知：
  - リバランス実行時（銘柄、数量、理由）
  - リスク停止発動時（ドローダウン率、停止理由）
  - エラー発生時（API接続失敗、注文失敗）
  - 日次パフォーマンスサマリー（リターン、ドローダウン、ポジション）

### 4.2 ヘルスチェックエンドポイント
**問題**: プロセスが生きているか、OpenDと接続しているかを外部から確認できない。
**改修**:
- 別スレッドでHTTPヘルスチェックサーバーを起動（`http.server` または `fastapi`）
- `/health` で以下を返す：
  - OpenD接続状態
  - 最終実行サイクル時刻
  - 連続エラー回数
  - 現在のリスク状態（停止中/通常運転）
- 外部監視（UptimeRobot等）からping可能に

### 4.3 データ欠損耐性
**問題**: `fetch_price_panel` で一部銘柄のデータが欠損すると全体が停止する。
**改修**:
- 欠損銘柄はログに記録し、残りの銘柄で処理を継続
- 欠損銘柄が3連続で取得できない場合、その銘柄を一時的にuniverseから除外
- ベンチマークのデータが欠損した場合のみ停止（ベンチマークは必須）

### 4.4 ログローテーションと構造化ログ
**問題**: 標準出力のみ。長期運用でログが肥大化。
**改修**:
- Python `logging` の `RotatingFileHandler` を導入（最大10MB、5世代保持）
- JSON形式の構造化ログ（日次の資産、ポジション、注文を機械可読に）

## Phase 5: ライブ取引安全機能（最重要：ライブ移行前必須）

### 5.1 注文前ダブルチェック
**問題**: ライブ取引時の注文ミスが致命的。
**改修**:
- ライブ注文前に、以下をログに出力し `webhook_url` に通知：
  - 注文予定の銘柄、サイド、数量、価格、想定金額
  - 現在ポジション vs 目標ポジションの差分
- `live_trade` コマンドに `--dry-run` オプション追加（実際には注文せず、チェックのみ）

### 5.2 デイリーロスリミット
**問題**: 1日で大きな損失が出る可能性。
**改修**:
- `config.py` に `daily_loss_limit_pct`（例: 5%）を追加
- 前日終値から当日のポートフォリオ評価額が5%下落した場合、すべてのポジションを清算し当日停止

### 5.3 ペーパー→ライブの段階的移行
**問題**: 一気にライブ移行するリスク。
**改修**:
- `config.py` に `live_allocation_pct`（デフォルト10%）を追加
- 初回ライブでは、総資産の10%のみをライブ戦略に配分
- 毎月ペーパーとライブのパフォーマンス差（スリッページ、手数料影響）を計測
- 3ヶ月間の追跡でペーパーとライブの差が2%以内なら、50% → 100%へ段階的に増額

### 5.4 緊急停止（Kill Switch）
**問題**: 異常検知時の停止手段がない。
**改修**:
- ファイルベースのキルスイッチ：`~/.moomoo_bot/KILL_SWITCH` ファイルが存在する場合、次サイクルで停止
- Webhook経由でのリモート停止コマンド受付
- 1時間あたりの注文回数上限（例: 10回超えたら停止、ループバグ防止）

## Phase 6: バックテスト・検証強化（推奨：継続）

### 6.1 追加パフォーマンス指標
- **Sortino Ratio**: 下方ボラのみを penalize
- **Calmar Ratio**: CAGR / 最大ドローダウン
- **回復期間分析**: ドローダウン期間、回復期間、ピーク→回復日数（`analyze_dd.py` を統合）
- **連続損失回数**: 連続するマイナス月のカウント

### 6.2 ウォークフォワードテストの自動化
- 現在の `research.py` は単発のtrain/test分割のみ
- ローリングウォークフォワード：毎年1月に過去3年で最適化、翌年を検証、を繰り返し
- 複数年の安定性を確認（1年だけ良くても採用しない）

### 6.3 マルチシナリオストレステスト
- 2020年3月（コロナショック）、2022年（ハイテク暴落）、2008年（リーマン）の期間を個別にバックテスト
- 各シナリオでのドローダウン、回復期間、最終リターンをレポート

## 実装優先順位マトリクス

| 優先度 | 項目 | 理由 |
|--------|------|------|
| **P0（即座）** | 状態永続化（SQLite） | 再起動でリスク状態が消えるのは致命的 |
| **P0（即座）** | 約定確認・ポジションreconcile | 注文だけ出して約定を確認しないとポジションがずれる |
| **P0（即座）** | キルスイッチ・デイリーロスリミット | ライブ移行時の安全装置 |
| **P1（1週間）** | コア・サテライト自動化 | ドローダウン-41%を避ける現実的な方法 |
| **P1（1週間）** | 動的サイジング（ボラターゲティング） | 高ボラ時の自動縮小でドローダウン抑制 |
| **P1（1週間）** | Webhook通知 | 異常に気づけないと運用継続不可能 |
| **P2（2週間）** | フォールバック資産有効化 | トレンド不在時の逃避先確保 |
| **P2（2週間）** | 週次リバランス | トレード回数増加で統計的信頼性向上 |
| **P2（2週間）** | データ欠損耐性 | 一部銘柄停止で全体が止まるのは運用上厳しい |
| **P3（1ヶ月）** | マルチタイムフレーム・逆ボラウェイト | さらなるリスク調整 |
| **P3（1ヶ月）** | ヘルスチェックAPI | 外部監視との連携 |
| **P4（継続）** | ウォークフォワード・ストレステスト | 長期的な戦略信頼性の検証 |

## 最短で全自動化するためのMVP構成

もし「今すぐ全自動化したい」なら、以下の最小限の改修だけでも大幅に改善します：

1. **SQLite永続化**（RiskState + 注文履歴）
2. **コア・サテライト構成**（VT 77% + アクティブ 23%）を `auto-run` に組み込み
3. **Webhook通知**（Discord/Slack）— リバランスとリスク停止のみ通知
4. **約定確認**— 注文後、次サイクルで `FILLED_ALL` 確認
5. **キルスイッチ**— ファイルベース停止機構

このMVPだけで、現状の「メモリ上だけの運用」から「再起動しても継続、異常を通知、緊急停止可能」な全自動運用の基盤ができます。
